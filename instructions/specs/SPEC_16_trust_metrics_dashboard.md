# SPEC_16 — Trust & Metrics Dashboard (answers "how do you report trustworthiness to a skeptical stakeholder")

Status: NEW. Currently: no metrics surface exists. `human_review_queue.jsonl`, `calibration_set.jsonl`, and audit logs contain the raw data needed, but nothing aggregates or reports it.

## 1. Research basis

Two separate bodies of work map onto this, and we fuse them rather than pick one:

1. **LLM observability platforms (2025 industry pattern)**: the current standard (Langfuse, Arize Phoenix, Traceloop/OpenLLMetry) is span-level tracing + an evals layer that sits *outside* the hot path, aggregating decisions after the fact rather than computing metrics inline (which would add latency — a mistake to avoid given your #2 latency priority). Pattern to copy: log a structured event per decision, aggregate asynchronously, render in a dashboard. Don't compute dashboard stats inside `pipeline.py`.
2. **Conformal prediction's own native metric — empirical coverage** (this is the fused, ControlPlane-specific part, not just "add a generic dashboard"): since SPEC_03 already frames your thresholds as conformal prediction, conformal prediction has a built-in, mathematically defensible trust metric — **empirical marginal coverage**: of all responses ALLOWed, what fraction were later confirmed (via human review) to actually be safe/correct? If your `tau` is calibrated for 95% coverage, you report the *actual observed* rate next to the *guaranteed* rate. This is a much stronger answer to a "skeptical stakeholder" than generic precision/recall, because it's the exact metric conformal prediction is designed to report, and it directly validates (or exposes) whether your calibration claim is real — which also quietly hedges the honesty gap already flagged about SPEC_03 being "rule-based dict lookups dressed as conformal prediction."

## 2. What to build

**A. Structured decision log (the data layer)**
Every pipeline run already produces a decision (ALLOW/MODIFY/REGENERATE/HUMAN) and a `FinalRiskReport`. Emit one structured record per run to a new `metrics_log.jsonl` (or a SQLite table if you're already doing #10 on the roadmap — reuse it):
```
{timestamp, use_case, decision_tier, risk_scores{perf,safety,bias,pii,cost}, overlap_flag, coverage_pct, latency_ms, human_verdict (nullable, filled later from review queue)}
```

**B. Aggregation job (the compute layer)**
A small script (`scripts/compute_metrics.py`, sibling to your existing `recalibrate.py` — same pattern, same trust level for judges) that reads `metrics_log.jsonl` + `human_review_queue.jsonl` and computes, per use case:
- Decision tier distribution (% ALLOW / MODIFY / REGENERATE / HUMAN)
- **Empirical coverage vs guaranteed coverage** (the conformal metric above) — this is your headline number
- False positive rate = human-reviewed cases where system flagged (MODIFY/REGENERATE/HUMAN) but human confirmed response was actually fine
- False negative rate = human-reviewed cases where system ALLOWed but human later found a problem
- Estimated cost saved = (responses that used MODIFY instead of REGENERATE) × average regeneration cost avoided, plus (Initial Router's small/medium model routing savings vs. always-large)
- Average latency per tier

**C. Dashboard (the presentation layer)**
Simplest defensible option for a hackathon timeline: a single HTML/Streamlit page reading the aggregation output — bar chart of tier distribution, one big number for coverage-vs-guarantee, a small table of FP/FN rates by use case. Do not build this as a live web service with auth etc. — a static-refresh dashboard you screenshot/demo live is enough; over-building this wastes time better spent on SPEC_09/#2.

## 3. Why this specific framing wins with judges

The PS asks: "how would you define, measure, and report false positive/negative rates and overall system trustworthiness to a skeptical stakeholder." Most teams will bolt on generic precision/recall. Your answer instead ties directly back to the conformal-prediction claim you're already making elsewhere in the pitch — a skeptical judge who asks "how do you know your calibration is actually working" gets answered by the same dashboard, not a separate hand-wave. That consistency across specs is what makes the whole submission read as one coherent system rather than eight disconnected components.
